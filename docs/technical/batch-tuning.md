# 정산 배치의 chunk와 fetchSize를 직접 측정했다

## 측정 대상

정산 명세 89,424건을 생성하는 Spring Batch Step에서 chunk와 fetchSize를 각각 바꿨다. 첫 실행은 워밍업으로 제외하고 이후 두 번의 평균을 비교했다.

## chunk 결과

| chunk | 평균 시간 | rows/sec |
|---:|---:|---:|
| 100 | 19.66s | 4,548 |
| 500 | 13.29s | 6,728 |
| 1,000 | 13.55s | 6,600 |
| 2,000 | 12.18s | 7,342 |
| 5,000 | 14.26s | 6,271 |

100은 커밋과 JDBC 왕복이 895회 발생해 확실히 느렸다. 500~5,000은 회차 편차와 비슷한 범위라 2,000을 최적값이라고 단정하지 않았다. 평탄 구간에 있으면서 청크당 메모리와 재처리 범위가 작은 1,000을 유지했다.

## fetchSize 결과

100, 1,000, 5,000이 모두 12.8~13.6초로 차이가 없었다. 원인을 확인하니 MySQL Connector/J는 `useCursorFetch=true` 없이 서버사이드 커서를 사용하지 않는다. 옵션을 켠 뒤에는 처리 시간이 약 20% 증가했고, 현재 요구에서는 적용하지 않았다.

## Reader 인덱스 판단

Reader 실행계획은 비효율적이었지만 읽는 대상이 520행에 불과해 13초짜리 배치에서 유의미한 병목으로 재현되지 않았다. 효과가 확인되지 않은 인덱스는 추가하지 않고 공연 수가 크게 증가할 때 재검토하기로 했다.

## 결론

설정값을 크게 만들수록 빠르다고 가정하지 않았다. chunk는 작은 값의 손해만 확인했고, fetchSize는 현재 측정 방식으로 효과를 증명하지 못했으며, Reader 인덱스는 대상 규모가 작아 적용하지 않았다.
