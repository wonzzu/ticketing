# 서버를 세 대로 늘리자 정산 배치가 세 번 실행됐다

## 문제 상황

단일 서버에서는 매일 한 번 실행되던 정산 스케줄러가 애플리케이션을 세 대로 확장하자 각 인스턴스에서 한 번씩 실행됐다.

정산은 날짜 단위 데이터를 삭제하고 다시 생성하도록 설계되어 순차 재실행은 가능했지만, 세 작업이 동시에 같은 날짜를 `DELETE & INSERT`하면서 서로의 결과를 덮고 데드락을 발생시켰다.

## 실제 관측

분산락 적용 전 실제 인스턴스 세 대에서 확인한 결과:

- 분당 배치 실행: **3회**
- 5분간 데드락 및 관련 오류: **20건**
- 타이밍에 따라 일부 정산 누락 또는 중복 상세 발생

단일 프로세스 테스트만으로는 발견할 수 없었고 동일 애플리케이션을 세 인스턴스로 실행하면서 드러난 문제였다.

## 지켜야 할 조건

- 같은 정산 날짜는 한 번에 한 인스턴스만 처리한다.
- 다른 인스턴스는 락을 기다리며 작업 스레드를 점유하지 않는다.
- 실행 중 예외가 발생해도 락이 영구히 남지 않는다.
- 취소 내역을 반영하기 위한 날짜 단위 재집계는 계속 가능해야 한다.

## 검토한 방법

| 방법 | 장점 | 판단 |
|---|---|---|
| Spring Batch 기본 중복 방지 | 같은 JobParameter 실행을 막는다. | 재집계를 위해 동일 날짜 재실행이 필요해 단독으로 사용할 수 없다. |
| DB 기반 잠금 | 추가 인프라 없이 구현 가능 | 정산 DB가 이미 부하와 데드락의 대상이어서 실행 조정까지 맡기지 않았다. |
| Redisson 분산락 | 모든 인스턴스가 공유하는 Redis로 실행 주체를 제한 | 기존 Redis를 활용할 수 있고 임대 시간과 비대기 획득을 지원한다. |

## 선택과 구현

스케줄러 시작 시 정산 날짜를 포함한 키로 `tryLock`을 호출한다. 대기 시간은 0으로 두어 락을 얻지 못한 인스턴스는 즉시 종료한다. 락을 얻은 한 인스턴스만 Spring Batch Job을 실행한다.

```text
Spring #1 ─┐
Spring #2 ─┼─ tryLock(settlement:daily:{date})
Spring #3 ─┘
              ├─ 성공한 1대: 정산 실행
              └─ 나머지 2대: 즉시 종료
```

배치 자체도 날짜 단위 삭제 후 상세 생성, 집계 순서로 구성해 순차 재실행의 멱등성을 유지했다. 분산락은 동시 실행을 막고, 배치 구조는 재실행 가능성을 담당한다.

## 검증

운영에서 관측된 0ms, 32ms, 45ms의 실행 간격을 테스트에 반영해 세 스레드가 같은 스케줄러를 호출하도록 재현했다.

- 동시 실행 시도: **3회 → 1회**
- 실제 환경 분당 실행: **3회 → 1회**
- 5분간 오류: **20건 → 0건**

## 남은 한계

- 분산락은 Redis 가용성에 의존한다. Redis 장애 시 중복 실행보다 정산 미실행을 선택한다.
- 정산 작업이 임대 시간을 초과할 가능성과 락을 가진 프로세스의 중단을 계속 고려해야 한다.
- 한 번만 실행되는 것과 한 번만 처리되는 것은 다르다. 외부 연동이 추가되면 각 처리 단위의 멱등성도 별도로 필요하다.
